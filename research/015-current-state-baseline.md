## Focus: Match Flow + Video Processing

This is the active work area. The two are tightly coupled: video recording is mounted *inside* the live-match step, and analysis playback is surfaced *inside* the (web) match wizard.

### Match Flow — mostly-working

**The real, shipping flow is the in-SESSION match.** An athlete joins a session lobby, challenges/random-matches an opponent there, and both run the live wizard. The OLD standalone head-to-head challenge flow on web is fully built but deliberately parked behind `redirect("/")`; on mobile it is **not built at all**.

**End-to-end (mobile — the polished path):** session lobby (`lobby.tsx`) creates the match via `createInSessionMatch` (in-session challenge confirm sheet) or `requestRandomMatch`, then `router.replace`s into the wizard on the `onMatchStarted` realtime signal. The 8-step state machine (`step-router.ts`: `weight → ready → live → end → result → confirm → summary`; `wait` is unused) is driven by DB status. `LiveStep` mounts the camera (best-effort, permission-tolerant), auto-records MP4, runs the timer + realtime pause/resume/end sync, keeps awake, fires haptics, and auto-ends 1s after timer expiry. Result recording validates submission winner/type/finish-time (must be ≤ match length, jits-ait), routes through the **offline mutation queue** keyed per-match, and broadcasts. Confirm/dispute go through the queue; `useMatchCompletion` auto-advances so users aren't stranded. Summary animates the ELO tick (ranked only), shows a signed delta and a weight-division-gap note when BE-stamped > 0, draws shown both-lose in amber.

**End-to-end (web — even richer):** the active wizard at `/session/[id]/match/[matchId]` computes an initial step including **timekeeper variants** (`timekeeper-wait` / `timekeeper-live` vs `fighter-live`) and threads a **chunked-video analysis viewer** (`match-recorded-step`, `match-summary-step`). `timekeeperEnabled` flag = true. Mobile has NO timekeeper role (variants collapsed; recording is per-device self-record only).

**Backend + storage side:** all RPCs are real and tested in `jr_be` — `start_match_from_challenge`, `start_match`, `record_match_result` (auto-calculates ELO; requires `status='in_progress'`), `confirm`/`dispute`/`resolve`, `pause`/`resume`/`end`, `create_session_match`, `cancel_session_match`, `random_match`. `calculate_elo_stakes` applies +50 phantom ELO × division gap to the heavier athlete and stamps `weight_division_gap`; draws always cost ELO. All flow through the typed shared mutations (`Result<T>`, never throw).

**What works:** the full mobile 8-step wizard + web timekeeper wizard, ready-check handshake, ELO-correct result recording, confirm/dispute auto-advance, animated summary, realtime sync. Pure helpers are unit-tested (`step-router`, `parse-finish-time`, `format-elapsed`, shared sync/timer hooks).

**What's partial / stubbed:**

### Video Processing — partial

**To the central question: YES, there is real server-side video PROCESSING — but it is gated behind un-deployed infra.** The full path record → upload → store → **slice → per-chunk AI analysis → merge** → playback exists in code on both apps and the backend and is genuinely sophisticated, not a stub.

**End-to-end:**
- **Mobile record + upload:** `LiveStep` auto-records MP4 (keep-awake, haptics, REC pill, auto-stop on end or 10-min cap; permission-tolerant). `upload-recording.ts` streams via `FileSystem.uploadAsync` (`BINARY_CONTENT`, no base64) to `match-videos/<matchId>/<uploaderAthleteId>/<ts>.mp4`, then `upsertMatchVideo` inserts the parent row at `status='ready'` (2GiB pre-flight check).
- **Web record + upload:** `use-video-recorder.ts` records WebM (vp9/vp8) at 854×480 via `MediaRecorder`, uploads the Blob via the storage SDK to the same canonical path (`.webm`), then `upsertMatchVideo` (live size guard, auto-stop at 2GB).
- **Backend processing (real):** `jr_be/workers/video-slicer/src/main.js` is a **1051-line production Cloud Run worker** (Dockerfile installs ffmpeg) that keyframe-accurately slices uploads into ~90s IDR-snapped chunks (re-encode fallback to stay under the analyzer memory ceiling), uploads chunks back to Storage, inserts `video_chunks`, and flips `match_videos` to `status='analyzing'`. `video-analyze-chunk` calls Gemini per chunk → `video_chunk_analyses`; `video-merge-analysis` consolidates into `video_analyses` (summary/positions/scoring_moments/technique_tags/recommendations).
- **Playback (web only):** `video-analysis-viewer.tsx` renders an HTML5 `<video>` from a 1-hour **signed URL** (private bucket, participant-gated RLS via `is_video_visible`), a live chunk-progress strip (`use-video-progress.ts`), and tabbed merged analysis. Surfaced only in the web timekeeper flow's `match-recorded`/`match-summary` steps.

**What's partial / stubbed / not-built:**
- **The slicer dispatch is inert unless deployed + configured** — `handle_match_video_slice_request` no-ops with a WARNING when `app.settings.video_slicer_url` GUC is unset; there is **no evidence the Cloud Run worker is deployed to production** (RUNBOOK describes a manual `gcloud` deploy + GUC wiring that appears not yet executed). In prod a row likely sits at `status='ready'` with no chunks, failing quietly.
- **Mobile has NO video playback or analysis viewer anywhere** — record-and-upload only; a mobile user can never watch their match or see the AI analysis.
- **Video/analysis is surfaced on NO athlete profile on either platform** — `get_athlete_videos` exists in types but is called nowhere; there is no "my match videos" gallery.
- **`get_video_progress`** is a documented Round-3 migration; the hook ships an `rpcMissing` degraded mode and the viewer footer can render "Realtime-only (RPC pending)".
- **No poster/thumbnail generation** (`athlete_stills` JSONB is unpopulated), **no transcoding / HLS / adaptive bitrate**, and the Mux/Cloudflare path in `video-webhook` is entirely commented-out Phase-2 STUB code. **No content moderation step.** `settings/video.tsx` is an explicit stub; `requested_tier` is hardcoded `'standard'`.

**Prioritized gaps/risks to tackle next:**
1. **"Looks built, may not run"** — the entire pipeline depends on an external Cloud Run worker that may not be deployed and a GUC that may be unset; the failure mode is a silent Postgres WARNING and a video stuck at `status='ready'`. **Confirm deployment + GUC wiring first.**
2. **Cross-format inconsistency** — web stores `.webm`, mobile stores `.mp4`; the ffmpeg slicer/chunk-extension logic assumes MP4, and **WebM won't play on Safari/iOS** until transcoding exists. Whether the WebM path slices cleanly is unverified.
3. **No mobile playback** — record-and-upload only; users can't view their own footage or analysis on the device they recorded on.
4. **Fragile mobile recorder lifecycle** — `recordAsync` resolves only on `stopRecording()`; a crash/unmount mid-record discards the clip silently, and two end paths (broadcast + `wrappedOnEnded`) could race to double-fire.
5. **Unobservable mobile upload** (`uploadAsync` emits no progress; spinner only, single silent retry) and **1-hour signed URLs minted per mount** (viewer open >1h breaks).
6. **`match_videos.status` has no state-machine guard** (client could PATCH it directly under `match_videos_update_own`) and the per-chunk Gemini fan-out has **no per-user rate limit / cost cap** beyond the 2GB size limit.

## As-built architecture

- **Monorepo (`jits_web`):** npm workspaces — `apps/web` (Next.js 16 App Router, Tailwind, shadcn/ui), `apps/mobile` (Expo SDK 54, expo-router, NativeWind v4), and `packages/shared` (`@jits/shared`) consumed by source (no build step). Typecheck crosses workspaces; the shared layer's clean typecheck + 188 tests is the integration backbone.
- **`@jits/shared` is the intended single data path:** ~36 queries + ~40 mutations + chat + 7 hooks, a `Result<T>`/`DomainError` model, offline geo. **Reality check:** the apps still make ~70 raw `.from()`/`.rpc()` calls, so the layer is the *primary* but not the *exclusive* data path it documents. Every hook takes the Supabase client as a param and injects platform behavior via callbacks — that's what lets one implementation run on web and RN.
- **Backend (`jr_be`, separate repo at `/Users/msponagle/code/EloRated/jr_be`):** 72 migrations, 33 RLS tables, ~95 functions (mostly SECURITY DEFINER RPCs), the two athlete triggers, weight-aware ELO, full match/challenge/session lifecycle, chunked video pipeline, push dispatch, gym-manager/owner-portal + admin/founder gating. Stats are **computed, not stored** (`athletes` has no `wins`/`status`-writable columns; `match_participants` SELECT is RLS-blocked). 1,286 pgTAP tests GREEN on a clean reset.
- **Realtime / presence:** Supabase Realtime; `app:online` presence is mounted and tracking on both platforms (web `worker: true` + external store; mobile AppState-aware + SecureStore tokens). The green dot is rendered on no live surface; `lobby:online` is unmounted dead code. Match flow rides broadcast channels + postgres-changes fallbacks.
- **Storage:** three private buckets — `athlete-photos`, `chat-images` (both in migrations), and **`match-videos` (config.toml ONLY, 500MiB, mp4/mov/webm/avi)**. Video delivery is signed-URL (1h), participant-gated by RLS. Server-side video processing runs out-of-band on a Cloud Run ffmpeg worker + Gemini Edge Functions, dispatched by a pg_net webhook gated on a per-environment GUC.
- **Push / infra:** mobile expo-notifications + web VAPID both register into `push_subscriptions`; DB triggers fire a real push Edge Function (Expo Push API + web-push) with per-category prefs and chat throttling. Mobile adds Sentry, deep-link handling, an offline NetInfo banner, and an in-memory FIFO mutation-queue consumed by the match record/confirm flow.
- **Deploy:** Vercel builds `apps/web` (`outputDirectory apps/web/.next`); mobile ships via EAS (real `projectId`/`updates.url`; OTA on the default channel). The repo-root `public/.well-known/` is NOT in Vercel's served path — a deployment wrinkle for universal links.

## Top cross-cutting gaps & risks

1. **Video pipeline "looks built, may not run."** The single biggest focus-area risk: server-side processing depends on an external Cloud Run worker (likely undeployed) + an unset `video_slicer_url` GUC; uploads succeed but silently never get sliced/analyzed. Confirm deployment + GUC wiring before treating video as functional, and decide on the WebM-vs-MP4 / no-transcoding playback story (WebM won't play on iOS).
2. **`eas.json` PRODUCTION profile points at `EXPO_PUBLIC_APP_ENV='staging'`.** A real store/TestFlight build would ship against staging env/data (and Sentry tagged `staging`). Verify and fix before any release build.
3. **Universal-link `.well-known` is doubly broken:** placeholder `TEAM_ID` / SHA256 AND tracked in the repo-root `public/` that Vercel never serves. Both the values and the file location must be fixed for iOS/Android app-link verification.
4. **Activation contract is split-brain.** The DB activates on `display_name + current_weight + (gym OR free_agent)`; `gender`/`date_of_birth` are frontend-only. Any non-canonical write path can create "active" athletes missing demographics the app assumes exist. Either enforce in the trigger or fix the docs.
5. **Session-lifecycle gating mismatch + missing web UI.** BE `sessions` UPDATE is creator-ONLY, but mobile offers activate/cancel/end to any manager (silent RLS no-op for non-creators), and web has NO session-lifecycle UI at all (the components exist but are test-only orphans). Reconcile the RLS policy with the intended manager model and build/wire the web UI.
6. **Match-flow has zero integration coverage and no crash-resume.** The state-machine orchestration, `recordMatchResult` round-trip, optimistic-queue reconciliation, and confirm/dispute paths are untested; a force-quit mid-match strands the match `in_progress` with no in-app re-entry. The `endMatch`-before-record footgun lives only in a comment.
7. **Fabricated/decorative data on shipped surfaces.** The web leaderboard ships a fabricated per-row ELO delta and 4 dead filter chips; gym stats show placeholder Avg ELO / hardcoded "Last Session". These are visible to users today and should be made honest (or built) before launch.
8. **Public, un-gated `/design/*` route in production** exposes the design system, screen inventory, and a Supabase-backed Founders Board to any visitor — a deliberate exposure decision is needed, not the current default-open state.
